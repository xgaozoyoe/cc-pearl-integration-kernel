Fold scheduling experiment on A-stream candidate; GPU0 only; 2026-10-08.

All measured variants: R128,K4096,CTA256x192,12warps,warp64x64,K64,
2operand stages,69632Bshared,1CTA/SM. Accumulators stay in registers.
Accepted V3/noise/target/proof implementations are untouched.

Control timeline (kt denotes K64 iteration):
 wait current copy -> CTA barrier -> async copy kt+1 -> LDSM/IMMA kt
 -> if kt odd, fold current R128 boundary.

Interleave (auxiliary, within same iteration):
 final K32 slice of boundary iteration: finish fragment j,
 finish fragment j+1 -> XOR/REDUX/store fragment j.
 Drain last fragment after final MMA. Static SASS confirms REDUX between
 MMA36..64 rather than all after64. This interleaves the complete fold,
 not just local XOR. Therefore a slowdown does not alone isolate XOR latency.

Crossloop (rejected before GPU timing):
 fold previous boundary immediately before each fragment's first new MMA.
 Fine-grained control increased pressure: initial68Bspill stores/loads,
 reordered version100Bstores/108Bloads. Not benchmarked or deployed.

Crossgroup (main user-requested experiment):
 wait current copy -> CTA barrier -> async copy kt+1 -> load operands
 -> for each N16 group in first K32 slice:
      fold its four previous-boundary M16 tiles, then advance their MMA
 -> second K32 slice MMA.
 Fold pending only for even kt>0, using rb=kt/2-1. Final kt63 boundary
 is folded explicitly before output. No stale or next-boundary values.
 SASS REDUX at IMMA counts0,8,16,24 in steady-state; final drain after64.
 168registers/thread,zero spill. This removes the fragment-level spill.

Handoff (cross-iteration memory overlap control):
 wait current copy -> CTA barrier -> async copy kt+1
 -> fold entire pending boundary -> LDSM/IMMA kt.
 New future cp.async can progress during prior-boundary fold.
 Same final drain as crossgroup.167registers/thread,zero spill.
 Code ordering proves the schedule change, not how many cycles overlap.
